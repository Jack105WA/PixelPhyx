# Current Project Context

_Last reviewed: 2026-11-20 (repository snapshot: `main` at `6e85f1b7152e002fe72167c85703b2ace5a7ca6c`)._

## Project

PixelPhyx is a browser-based 2D pixel physics and chemistry simulator with a standalone offline edition and a self-hosted WebSocket multiplayer relay.

- Production site: https://jack105wa.github.io/PixelPhyx/
- Repository: https://github.com/Jack105WA/PixelPhyx
- Active development branch: `main`
- Production deployment: GitHub Pages, built by `.github/workflows/pages.yml`
- Simulation engine: Rust compiled to WebAssembly
- Browser orchestration and UI: JavaScript/TypeScript
- Multiplayer relay: Node.js WebSocket server in `Server/`

## Current focus and architecture

The simulation runtime is in `Website/`. The entry page is `Website/index.html`; the main runtime is `Website/js/main.js` with corresponding TypeScript source at `Website/js/main.ts`. The runtime imports separate material, physics, WASM, UI, life, and multiplayer modules.

The Rust crate is `Website/wasm/`. Its current modules are chemistry, engine, grid, input, render, rigid bodies, and ropes. The browser wrapper is `Website/js/wasm-engine.ts`. The generated wasm-pack package is currently present in `Website/pkg/`.

The offline edition is `Offline/offline.html`, generated by `Offline/build-offline.mjs`. It embeds the browser application, generated WASM glue/binary, font, and required assets into one HTML file. It disables multiplayer and must remain usable from `file://`.

The server in `Server/` is a separate relay and local hosting package. It downloads/caches the website and uses isolated headless browser sessions for authoritative room simulation. It is not a hosted public matchmaking backend. Do not describe an IP-server as functional unless its actual protocol/backend is implemented and verified.

## Known issues and documentation cautions

1. The required `Agents/` documentation directory did not exist before this documentation set was added.
2. `README.md` says generated WASM package artifacts are not committed, but `Website/pkg/` currently contains tracked generated JS, declarations, and a WASM binary, and `build-wasm.yml` commits generated package output. Reconcile the README with the actual build/release policy.
3. `Website/js/*.ts` and `Website/js/*.js` are paired source/runtime files. The TypeScript build writes JavaScript into the same directory. Make TypeScript edits in the source file and verify the generated/runtime JS is updated; do not assume every pair is byte-identical.
4. The WASM README contains historical branch references and migration notes that may not describe the current `main` branch. Verify them against the current implementation before relying on them.
5. No manual browser test, offline `file://` test, Rust test suite, or end-to-end multiplayer test was run as part of this documentation-only task.
6. The relay keeps room state in memory; it is not persistent across server restarts. HTTPS clients require WSS.
7. A recent offline build was generated by CI, but do not mark the whole offline feature completed solely from that generated commit.
